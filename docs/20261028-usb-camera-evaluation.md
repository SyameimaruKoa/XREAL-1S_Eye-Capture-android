# USB Camera と映像品質の調査（2026-10-28）

## 既存アプリの試験

インストール済み USB Camera 12.3.0 で、XREAL 1S の USB 2.0 接続と HEVC 2048×1512 のプレビューを確認した。表示フレームレートは約59.4 fps。HEVC Bypass のアプリ内説明は、UVC の HEVC を IP Camera Server に再エンコードせず出力するとしており、ローカル録画のバイパスを保証していない。

約21秒のローカル録画試験では、出力 MP4 は約4 KB で映像フレームを認識できず、ログには 2048×1512・30 fps の AVC エンコーダ起動が記録された。この試行は使える録画にならなかったが、すべての設定でローカルの無変換録画が不可能と証明したものではない。音声の入力元も未確認。アプリには USB 音声が利用できない場合に端末マイクへ切り替える旨の警告があり、独立ステレオの実現は確認できていない。

ユーザーの許可で IP サーバーを一時起動した。HTTP 8081 と RTSP 8554 が全インターフェースで待ち受け、認証なしでは RTSP は 401 を返した。設定済み認証情報での接続は TCP 接続まで確認できたが、試した `/live` では制限時間内に映像情報を取得できず、HEVC の無変換保存は未検証。終了時点では両ポートの待受がないことを確認した。URL や認証、サーバー側状態を含め原因は未確定。

インストール済み APK の `assets/www/main.html` をオフラインで確認したところ、Web プレーヤーは `/live.flv` を指定していた。これは HTTP 側の別の検証候補であり、その経路が HEVC バイパスを扱えることや、前回の RTSP 接続失敗の原因は示さない。APK の文字列には `/live` と `/live ...` もあるが、文字列だけでは RTSP の正しい完全な URL を証明できない。今回サーバーは再起動していない。

ユーザーが XREAL を再接続した後、既存の UVC 有効化操作で11インターフェースに移行し、USB Camera の HEVC 2048×1512 プレビュー約59.4 fps を確認した。許可済みの一時試験として HTTP サーバーを起動し、設定済み認証を使用して `/live.flv` を要求したが、8秒の制限時間内に応答を受け取れず HEVC 保存は未確認。HTTP 8081 の待受は試験後に停止した。原因は不明。ユーザーは今後同じ接続不良が再発した場合、スマートフォンの再起動による復旧を許可した。今回の復旧には再起動を要しなかった。

追加の HTTP 試験では、認証なしの `/` は 401、設定済みの Basic 認証を付けた `/` と `/live.flv` はいずれも 200 を返した。`/live.flv` の応答本文は6秒の受信待ちで FLV ヘッダ13 bytes のみで、映像や音声のタグは得られなかった。従って前回のタイムアウトは HTTP 応答そのものがなかったと断定できず、取得要求の読取待ちを含む。認証情報をログに残さず、試験後に8081と8554の待受がないことを確認した。配信が止まる原因や HEVC バイパスの正否は未確定。

アプリ内の接続案内で、RTSP のパスが実際に `/live`、HTTP FLV のパスが `/live.flv` と確認できた。RTSP サーバーを一時起動して要求を分けて調べると、`OPTIONS` は 200、同じ認証情報を Basic 形式で付けた `DESCRIBE` は 401 だった。HTTP と RTSP の認証方式や設定が同じとは限らず、これだけで映像側の不具合とは断定できない。試験後に両ポートの待受がないことを確認した。

さらに RTSP の認証要求を確認すると Digest 認証だった。提示された realm と nonce を使い、HTTP と同じ設定済み資格情報で Digest 応答を生成して DESCRIBE を再送したが、8秒以内に応答がなく SDP を得られなかった。401 とも成功とも判定できず、資格情報の妥当性や映像配信状態は未確定。試験後に両ポートの待受を停止した。

後から読み出した端末ログには USB Camera プロセスの AVC ハードウェアエンコーダが起動・停止した記録もある。ただし、確認した抜粋だけでは特定の配信要求との時間的対応や、そのエンコーダの出力が配信されたかを確定できない。HEVC バイパスの設定表示だけをもって配信が無変換だったと判断しない。

設定ファイルの読み取りでは `hevc_bypass=true`、`hw_encoder=true`、`flv_format=0`、`rtsp_format=0` だった。これらの数値の意味や優先関係はアプリの設定実装を確認できておらず、設定値だけで出力コーデックを決めつけない。再度短時間サーバーを切り替えた際のログ抜粋では対象エンコーダの起動行を取得できなかったため、前述の AVC 起動との対応は未解決。試験後のポート待受はなかった。

設定画面で確認したところ、以前の `rtsp_format=0` と `flv_format=0` はどちらも H.264 + AAC を示し、RTSP には HEVC + AAC の選択肢がある。RTSP を HEVC + AAC に変更したが、設定画面から戻った後にプレビューが黒画面になり、この設定での配信検証は行えていない。元の H.264 へ戻す操作も試みたが、設定ファイルは `rtsp_format=1` のままであり、元に戻せていない。サーバーは起動していない。表示設定と実際のバイパス動作は区別して検証する。

その後、ユーザーがスマートフォンの起動を確認し、ADB・SSH は復帰した。再起動後に UVC を有効化すると USB Camera の HEVC プレビューが復帰。RTSP HEVC + AAC 設定で一時サーバーを起動し、認証付き ffprobe は HEVC 2048×1512 と AAC を検出した。ffmpeg の映像ストリームコピーで保存した約7.996秒の MKV は映像448パケット、全デコードでエラーなし。この試験では音声を保存していない。受信側で再エンコードしていないことは確認できたが、USB Camera が入力 HEVC をバイト単位でそのまま送ったかは未比較。サーバーを停止し待受がないことを確認した。RTSP 設定は引き続き HEVC + AAC。

この RTSP 映像のみの MKV は 1,935,813 bytes / 7.996秒で、コンテナ込み約1.94 Mbps。先頭120パケットの `init_qp_minus26` は0、`slice_qp_delta` は8が4、11が106、12が10で、自作録画の先頭120パケットと近い。別時刻の映像なのでバイト一致やパススルーの証明ではないが、少なくともこの配信では本体直接録画の約34 Mbpsに相当する高ビットレートは得られていない。RTSP ファイルの `avg_frame_rate=90/1` は実測 fps と扱わない。

## 本体録画との画質比較

ユーザーは自作アプリの映像が本体直接録画より非常にノイジーと報告した。23:36 の自作アプリ録画は HEVC 2048×1512、映像平均約 2.05 Mbps。raw HEVC と MP4 の映像 VCL NAL は既存調査で全4,289個が一致し、この録画の全デコードで FFmpeg エラーはなかった。これは保存・コンテナ格納による再エンコードを支持しないが、カメラ側の圧縮、露出やノイズ処理、UVC 受信以前の品質、または他の受信上の問題を除外しない。ビットレートだけで画質劣化の原因は断定できない。

本体の直接録画と自作アプリ録画を同じ場面・照明で比較し、解像度、フレームレート、ビットレート、静止画のノイズと細部、および各経路の設定を調べる。USB Camera のプレビューを同条件で比較する際は、前回試験中にカメラ調整画面で意図せず設定値に触れた可能性があり、元の値も不明な点に注意する。RAW 独立ステレオ以上の音声調査は引き続き別キューに残る。

ユーザー提供の本体録画 `logs/VID_0032.mp4` を確認した。約60.57秒、映像は HEVC 1600×1200、平均約59.39 fps、34,019,053 bit/s。音声は FLAC 48 kHz・2ch。自作アプリ録画の約2.02〜2.05 Mbps と比べて映像ビットレートは約16.6〜16.8倍だが、解像度や撮影場面が異なるため、差の全てをノイズの原因とは断定できない。直接録画と UVC のエンコーダ設定・経路の違いが画質調査の重要な候補となった。

本体録画の FLAC 音声全体を 32-bit PCM に展開し、左右 2,906,496 フレームを比較した。左右のサンプル値が一致したのは3フレームで、左右の全体の Pearson 相関係数は約0.2815。よって少なくともこの本体録画の2チャンネルは同一のデュアルモノではない。ただし異なる信号であることだけでは、物理マイク個別の RAW、加工なし、または独立した収音源であることは証明できない。UAC経路との違いと元データの取得方法は引き続き未解決。

同じ音声を先頭から10秒単位で分けた左右相関は、完全な6区間で順に 0.2601、0.3086、0.2748、0.3514、0.1887、0.2860。各区間で左右のサンプル値が等しいフレームは0または1だった。録画全体の差が一部の区間だけに偏った結果ではないが、前述のとおり物理的な音源の独立性や未加工性は判定できない。

両動画の冒頭120映像パケットを `trace_headers` で比較した。どちらも HEVC Main・8-bit、PPS `init_qp_minus26=0`。本体録画の `slice_qp_delta` は -4〜1、自作アプリ録画は 8〜12 で、自作側が高かった（それぞれ120スライス）。シーンは異なるが、この範囲の圧縮パラメータの差と約17倍のビットレート差は、UVC 側の強い圧縮が画質劣化に関係する有力な証拠である。スライス単位の値だけで各画素の最終 QP や、全区間の品質・発生層は確定できない。機器の UVC HEVC エンコード設定を実際に変更できるか、取得可能な制御と検証方法を優先して調査する。

追加で自作アプリの10月27日の7録画を `ffprobe` で調べたところ、映像平均ビットレートは 2,023,932〜2,053,780 bit/s だった。長時間録画の映像パケットサイズを10秒ごとに集計すると、19:36 の完全な10秒区間は約 2.009〜2.053 Mbps、19:48 は約 1.682〜2.082 Mbps、20:08 は約 1.986〜2.064 Mbps。最後の部分区間は除外した。時間区間の実測は一定付近への集中を示すが、固定ビットレート設定や画質低下の原因を証明しない。

現行ソースの UVC probe は圧縮品質 `wCompQuality` に0を指定し、`dwMaxVideoFrameSize` に 5 MiB を指定する。後者はフレームサイズに関するフィールドであり、5 Mbps の映像ビットレート指定ではない。GET_CUR の返値を COMMIT に使っているが、この記述だけでは実際の圧縮設定値、機器がこれらのフィールドをどう解釈したか、本体録画との違いを確定できない。撮影設定を変更する前に、記録された probe と機器側が提供する設定・本体録画の実データを調べる。

保存済み `logs/p4_uvc_desc.txt` の USB ディスクリプタを読み直すと、IF10 の HEVC フレーム1は 2048×1512、記載された最小・最大ビットレートはそれぞれ 247,726,080 / 495,452,160 bit/s。これは機器がディスクリプタに記載した値で、実際に撮影された映像の平均約2 Mbpsとは大きく異なる。ディスクリプタ値を実効ビットレートや選択可能な圧縮設定と見なす根拠はない。別の保存済み `logs/p16/p16_uvc.log` の GET_CUR はフレーム間隔 166666、最大フレーム 5,242,880 bytes、最大 payload 262,144 bytes を返したが、圧縮品質の返値はログにない。

別プロジェクトの調査資料には RGB カメラの露出関連 SDK 要求名があるが、UVC HEVC 録画との関係や設定値は確認されていない。名前だけを根拠に機器へ送信しない。

同資料 `.research/xreal-linux/docs/xreal-link-messages.md` には、SDK の `NRRgbCameraInitSetCompression`（要求 ID 10223、入力フィールド1が varint）も記載されている。圧縮設定を調べる具体的な候補だが、列挙値の意味、ビットレートとの関係、UVC 出力への適用、1S での動作は未確認。同資料の 52995 等の過去の無応答と別の制御プロトコルの説明を混同せず、値を推測して送信しない。

手元の `ControlGlasses-3.1.0.apk` の `libnr_service.so` をオフラインで検索すると、この要求に対応するログ文字列の引数名は `enable` だった。ビットレートの数値を指定する API だという根拠は得られず、文字列だけで実際の型・値・動作や UVC への影響を確定することもできない。SDK のバージョンと対象機器にも注意する。

保存済みディスクリプタの VideoControl IF9 を解析すると、Extension Unit 4 の GUID は `a29e7641-de04-47e3-8b2b-f4341aff003b`、制御ビットマップは `00 00 00` で、この記述上は利用可能な XU 制御が示されていない。IF9 に標準 Encoding Unit の記述も見当たらない。これは標準的な公開情報からビットレート制御を特定できなかったという結果であり、機器独自の制御や別経路が存在しない証明ではない。[Linux UVC ドライバーの説明](https://www.kernel.org/doc/html/v4.9/media/v4l-drivers/uvcvideo.html)では XU の直接照会にはユニットとセレクターが必要で、GET_INFO で GET/SET 対応を確認できるとしているが、未確認のセレクターを推測して変更することはしない。

[XREAL の本体撮影・ファイル管理の公式案内](https://tutorials.xreal.com/docs/accessories/eye/how-to-use/capture-and-file-management/)は、直接撮影したファイルがグラス内に保存され、利用可能容量は 2 GB、転送モードで `XREAL/DCIM/` から取り出せると説明する。今回の本体録画は高ビットレート・左右別信号の音声を持つため、そのまま取り出す経路は短い撮影の比較対象となる。ただし容量・撮影時間の制限があり、連続長時間のスマートフォン録画や録画中の無変換転送を満たすことは確認できていない。

## UVC / UAC 以外の候補（ユーザーの追加指示）

再起動後、スマートフォンには XREAL 側 USB Ethernet の `169.254.2.10/24` と `169.254.1.10/24` が存在した。`169.254.2.1` への ping は応答しなかったが、ICMP 無応答は TCP の可否を意味しない。手元の別プロジェクト資料には RGB カメラ操作に対応する TCP 制御メッセージ名と、音声の開始・モード・アルゴリズム関連メッセージ名がある。検索結果には One + Eye の TCP 52995 経由 HEVC 映像を扱う実装の説明も見つかったが、該当リポジトリは取得時点で 404 のため本文や実装を検証できていない。1S での映像・音声対応、ビットレートと独立チャンネル数は未確認。既存の調査資料・公開実装のコードを検証し、UAC の直接 claim/release を避けて映像と音声それぞれのデータ経路を調べる。

同じ端末から `nc -z -w 2` で `169.254.2.1` の TCP 52999 と 52995 をそれぞれ確認したところ、どちらもタイムアウトした。接続要求のみでデータやカメラ開始コマンドは送っていない。これは今回のネットワーク状態での結果で、機器の別アドレス、初期化状態、TCP経路の存在や有効化可能性を否定しない。手元の `.research/xreal-linux/docs/xreal-link-messages.md` は別環境の XREAL 1S で 52999 の読み取り要求に応答した実績を記録しており、接続先・構成の違いを先に調べる。

**上記タイムアウトの訂正・切り分け:** Android の `ip route get` では、通常の `169.254.2.1` 宛通信は USB の eth0 ではなく Wi-Fi の wlan0 のゲートウェイに向いていた。送信元アドレスを指定しても同様だった。eth0 / eth1 を明示した ping はそれぞれ `169.254.2.1` / `169.254.1.1` から応答した。さらに `socat` の `so-bindtodevice=eth0` で TCP 52999 と 52995 への接続成功を確認した。データや状態変更コマンドは送っていない。従って先のタイムアウトは適切な USB 経路を試せておらず、これらのポートが閉じている証拠ではない。TCP 接続成功は RGB 映像や高品質音声が取得できる証明ではない。

同じ eth0 指定の TCP 52999 に、別環境で実証済みのソフトウェアバージョン読み取り要求 `0x271d` を1回送信し、対応するトランザクション ID の34 bytesの応答を受けた。接続直後に入力を閉じた試行は応答0 bytesだったが、入力を開いたまま待った試行では応答を得た。これによりスマートフォンから XREAL 1S の制御経路を実際に使えることを確認した。カメラ開始や音声設定は送っておらず、映像・音声データ取得はまだ未確認。

音声関連の読み取り要求 `NRAudioGetCurrentMode`（10091）、`NRAudioGetDefaultMode`（10093）、`NRAudioGetAlgorithm`（10101）にもそれぞれ応答があった。前二者の応答ボディは空の入れ子 `22 00`、最後は `22 02 10 01`（フィールド2の値1）。値の列挙定義と、これがマイク処理や UAC 出力にどう対応するかは未確認。音声モード・アルゴリズムの変更や音声取得開始は行っていない。

RGB の読み取り要求 `NRRgbCameraGetConfig`（10243）はカメラ校正 JSON を返し、`resolution` は 2016×1512 だった。校正用センサー情報であり、現在の TCP ストリーム解像度や選択可能な出力モードを示す証拠ではない。`NRRgbCameraInitSetImageResolution` の要求名も資料にあるが、値の意味や呼び出し順は未確認。未検証の値を機器に書き込んでいない。

公開検索結果に残る One + Eye の TCP 映像開始 `0x2781`・停止 `0x2782` とポート52995の説明を参考に、スマートフォンから eth0 指定で映像ポートを先に接続し、開始後約6秒で停止した。制御側はいずれも対応する ACK `22 00` を返した。映像ポートで 2,554,319 bytes を受信し、完全な `0x2785` フレーム46個から Annex-B 開始コード以降を取り出すと HEVC 1280×720 が得られ、FFmpeg でエラーなくデコードできた。末尾32,768 bytes は途中で切れたフレームとして除外。接続・停止時の部分取得であり fps、ビットレート、安定性や高解像度への設定可否は未検証。UVC を経由しない映像データの取得を実機で確認したが、UAC 以外の音声はまだ取得していない。参考の検索結果の元リポジトリは前述のとおり現在取得不可であり、その手順を 1S で実測した結果として記載する。

抽出した HEVC は 2,519,245 bytes、FFmpeg が復号した映像は45フレーム。全スライスの `init_qp_minus26=0`、`slice_qp_delta` は -11〜-3 だった。自作 UVC 録画の冒頭120スライスの8〜12より低く、強い圧縮になっていない可能性を示す。ただし撮影時刻・解像度・フレーム種別が異なり、スライス値だけで画質は定量比較できない。`r_frame_rate=30/1` はストリームからの推定で、到着時間付きの実測値ではないため、この短い試験のビットレートや実 fps は計算しない。

### 追加候補: 別形式の UVC

[xreal-eye-stream の公開実装](https://github.com/AlfaKeNTAvR/xreal-eye-stream/blob/main/README.md) は One Pro + Eye の Linux 向け利用例として UVC の MJPEG 1920×1080・60 fps を記載している。手元の 1S の保存済み USB ディスクリプタにも format 2 の MJPEG と 1920×1080 のフレーム記述があり、別形式の UVC として次に実機比較する候補になる。ただし One Pro の記載は 1S での成功を保証しない。1S の MJPEG 実効 fps、ビットレート、画質、長時間安定性、既存アプリでの元データ保存、および音声の独立性は未検証。MJPEG を無変換で扱えるコンテナとアプリの動作を確認し、HEVC に変換した録画をパススルーとは扱わない。

USB Camera の実機試験では、カメラを有効化後、元の HEVC 2048×1512 プレビューが約59.4 fps と表示された。形式選択に MJPG 1920×1080 があり、適用後はプレビューが黒画面になり約13秒間映像・fps 表示が得られなかった。適用前のダイアログには60.0pが表示されていたが、再度開いた時は30.0pであり、機器に実際に設定されたフレームレートは特定できない。アプリは黒画面の場合に解像度やフレームレートの変更、場合によっては再接続を案内している。この1回の試験では MJPEG 取得に成功しておらず、全モードの不可を示すものではない。試験後に USB Camera の設定を HEVC 2048×1512・60p に戻し、保存された設定を確認してアプリを停止した。

**追加試験:** MJPG 1920×1080・30p を明示してアプリを再起動すると、映像が表示され、アプリ内に約29.8〜29.9 fps と表示された。再起動後の MJPG 1920×1080 の設定画面では30pと25pが選べ、60pは表示されなかった。したがって前述の切替時の60p表示だけで、このモードが60 fps対応とは判断しない。

同設定で約25.3秒のローカル録画を行うと、MP4 は映像752フレーム、1920×1080、H.264 約15.54 Mbps、AAC 音声を含んだ。録画時ログには AVC エンコーダの起動があり、MJPEG をそのまま保存したものではない。音声の入力デバイスと独立性は未確認。このアプリの別設定でも無変換保存が不可能という証明ではない。試験後、設定を HEVC 2048×1512・60p に戻し、保存値を確認してアプリを停止した。元データは `logs/mjpeg_usb_camera_trial.mp4`（Git 管理外）。

この MP4 の音声は AAC 48 kHz・2ch だった。全区間を32-bit PCM に展開した1,215,488フレームについて比較したところ、左右のサンプルは全て一致した。無音ではなく左右のピークは 21,383,758、RMS は約792,632（32-bit PCM 値）だが、今回得た音声は独立したステレオではない。音声が XREAL とスマートフォンのどちらから取り込まれたか、AAC 以前にどこで同一化されたかは確認できていない。

既存 USB Camera の設定ファイルを読み取ると `mjpg_bypass=true`、`mjpg_correction_2=false` だった。[アプリの過去の変更履歴の転載](https://apptopia.com/google-play/app/com.shenyaocn.android.usbcamera/about)には、MJPG ByPass を IP Camera Server 向けの再エンコード回避機能として追加した旨がある。前述のローカル録画とは別の出力経路であり、当該設定値だけでは現在のアプリバージョンで無変換配信されたことは証明できない。次に認証付きの一時サーバーで MJPEG ストリームを取得し、コーデック・受信量・画質・停止を検証する。独立音声は別途検証する。

MJPG 1920×1080・30p に設定してアプリを再起動し、一時 IP サーバーを起動した。アプリの接続案内に MJPEG の `/video` が示され、認証付き HTTP は 200、`multipart/x-mixed-replace` を返した。約8秒で 21,156,982 bytes を受信。完全な multipart 画像237件の画像本体は合計21,139,611 bytesで、先頭と末尾を確認すると236件は JPEG の SOI/EOI を持ち、1件は SOI がなく EOI はあった。末尾73 bytes は受信終了で途中になったデータ。個別画像のバイト同一性はカメラ入力と比較しておらず、設定どおりのバイパスとは未証明。先頭欠落が機器・USB・アプリ・HTTP処理のどこで生じたかも未特定。結合したデータは FFprobe が 1920×1080 MJPEG と認識し、FFmpeg の全体デコードではエラー出力がなかったが、これだけでは各 multipart 画像の完全性を保証しない。音声は取得していない。試験用サーバーの待受停止を確認し、アプリの設定を HEVC 2048×1512・60p に戻して停止した。受信データは `logs/mjpeg_http_trial.multipart`（Git 管理外）。

この異常な multipart 本体をさらに確認すると、先頭から85,444 bytes の位置に JPEG の EOI があり、直後に別の SOI が続いて、末尾の EOI まで89,235 bytes が存在する。つまり単に1枚の先頭が欠けただけではなく、先頭のない画像末尾と、別の画像データが同じ multipart 本体に連結していた。前後の multipart 境界と Content-Length は記録上整合しており、HTTP の長さ区切りを無視した解析が生んだ見かけの連結ではない。発生箇所と、後続画像が完全に正常かどうかは未確定。

後半89,235 bytes を独立したファイルとして取り出すと、FFprobe は1920×1080 JPEG と認識し、FFmpeg の単独デコードはエラー出力なしで終了した。先頭のない前半85,444 bytes は単独デコードできなかった。後半の画素内容の完全性を保証するものではないが、この試験では少なくとも連結された後半を復号できる。元データの保存や録画時の自動修復は行っていない。

### Windows での MJPEG 比較

ユーザーが XREAL を Windows に挿し換えた後、1S の HID 制御で現 USB 構成 `0x0000AA55` を読み取り、UVC を有効化する `0x00019A55` を送って `UVC Camera 0` を確認した。DirectShow は MJPEG 1920×1080 の60pおよび30pのモードを提示した。FFmpeg の DirectShow 入力で `-c:v copy` により30秒ずつ MKV に保存したところ、60p指定は1,800パケット・約30.009秒、30p指定は900パケット・約30.004秒だった。出力側での再エンコードは行っていないが、カメラからアプリに届くまでのバイト同一性は別途未検証。音声は取得していない。

各 MKV の全パケットを個別に取り出して JPEG の SOI/EOI を数えると、両試験とも最初の2パケットは各320 bytesの全ゼロで JPEG ではなかった。60pの残り1,798件と30pの残り898件は、それぞれ先頭 SOI・末尾 EOI を1組ずつ持ち、隣接する画像データの完全一致は0件。取得開始時の非 JPEG パケット以外に、先の Android HTTP 試験で見た連結や先頭欠落はこの範囲では観測されない。これは30秒の構造検査で、全画素の正しさ、長時間安定性、カメラ・OS間の欠落の不在を保証しない。Windows では短時間の60p取得が可能で、Android アプリの設定画面に60pが表示されなかったことを1Sのハード上限と見なせない。元ファイルは `logs/windows_mjpeg_60.mkv` と `logs/windows_mjpeg_30.mkv`（Git 管理外）。

[XREAL SDK 3.0/3.1 の公式リリースノート](https://developer.xreal.com/download/)は Eye 対応と Android での ControlGlasses 利用を記載している。SDK 2.4 の RGB カメラ項目には YUV_420_888 への変更も記載されるが、これは SDK が提供する画像形式の説明であり、今回の TCP HEVC の解像度・fps の変更方法や無変換録画機能を示すものではない。3.1 のダウンロードページには利用規約への同意項目があり、今回その同意や SDK ダウンロードは行っていない。手元の ControlGlasses 3.1 バイナリの文字列と既存プロトコル資料では、解像度指定値の意味を特定できなかった。

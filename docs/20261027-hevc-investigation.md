# 長時間録画の HEVC 参照エラー調査

## 対象と事実

2026-10-27 19:36:48 の録画は約178.82秒、2048×1512、映像パケット10,624個。raw HEVC と MP4 から取り出した映像 VCL NAL は全数一致している。元の WAV は全サンプルがゼロ。

時刻付き FFmpeg デコードでは、約125.7秒付近に HEVC の `Could not find ref with POC 7`、`Error constructing the frame RPS`、`Skipping invalid undecodable NALU` が発生した。デコード済みフレームは10,599個（I 355、P 10,244）で、入力パケット数より25個少ない。フレーム数の差はこのデコード環境での結果であり、発生元を示すものではない。

同じ箇所の HEVC ヘッダを FFmpeg `trace_headers` で確認した。125.734秒の IDR の後、`first_slice_segment_in_pic_flag=1` の P ピクチャの POC は 1, 2, 3, 4, 8, 8, 8, 8, 9, 10... と記録された。5～7 がなく、8 が4回続く。異常な POC を持つ VCL NAL も raw HEVC と MP4 の双方に同じ順序で存在するため、MP4 への格納後の改変は原因ではない。

4つの POC 8 の NAL を、MP4 の4バイト長フィールドを除いて直接比較した。長さは順に 3,385、3,492、4,363、5,010 bytes で、隣接する組はそれぞれ短い NAL 全体が長い NAL の先頭にバイト単位で完全一致する。つまり同じ先頭データに末尾が段階的に増えた形であり、単なる POC 値だけの偶然の一致ではない。raw HEVC の VCL 順序との一致は前述のとおり。この結果は受信データの再利用や断片の誤った組み立てなどを調べる根拠になるが、どの層で起きたか、元のカメラ信号がどうだったかはまだ分からない。

長さ512 bytes以上の連続するパケットを同じ方法で比較すると、19:36の録画では10,624パケット中この異常箇所に限って3組が完全な前方一致を示した。比較用の23:36の72秒録画（4,289パケット）と10月21日の34秒録画（2,040パケット）では0組だった。この限られた比較は、前方一致が必ず故障を意味することを証明しない。

10月27日の撮影5本すべてを同条件で追加比較した。19:40（13,233パケット）と20:03（14,062パケット）は0組、19:48（52,470パケット）は2組、20:08（54,584パケット）は3組だった。19:48の異常は約602.41秒、20:08は約917.78秒付近。該当部分の `trace_headers` では、19:48は POC が4から15へ飛んだ後に15が3回、20:08は10から14へ飛んだ後に14が4回続いた。各異常直前の MP4 パケット到着時刻にはそれぞれ約321ms、約144msの間隔があり、その後1〜2ms以下の短い間隔で連続した。撮影5本中3本で同種の現象を確認したが、長い間隔と POC 異常が相関することは原因や欠損場所の証明ではない。

撮影5本中、100ms以上のパケット時刻間隔は計5箇所。このうち3箇所は後続12パケット以内に前方一致があったが、19:48の別の2箇所（約181.22→182.29秒の1,068.6ms、約184.01→184.71秒の693.9ms）ではなかった。179.5〜185.5秒を `trace_headers` で確認した範囲でも POC の不連続は検出されなかった。ただし前者は長い間隔の後に IDR があるため、間隔中の欠落を POC だけで否定できない。100ms以上の間隔そのものを原因や破損と断定できない。

MP4 の IDR とその次のパケット間は約138.76ms、その後は約0.5～3.6msで複数パケットが連続する。異常と時刻の集中は同じ周辺で生じているが、これはカメラ、USB 転送、Android 側の受信処理、書き込み・ログなどのどれが原因かを証明しない。撮影時の UVC ごとの詳細ログは確保されていないため、過去の信号を復元することはできない。

確認に使用したローカル資料: `logs/xreal_20261027_193648.mp4`、対応する `.hevc`、`logs/goal_hevc_showinfo.log`、`logs/goal_hevc_headers.log`。大きい録画とログは Git に含めない。

## 次の検証

## 再現試験の中断（23:37 JST）

UVC が11インターフェース、480 Mbps で認識されていることを確認し、既存アプリで約72秒の録画と logcat の取得を行った。停止 intent を送った直後に adb が `error: closed` / offline となり、SSH もタイムアウトした。logcat の末尾は23:37:49.108で、取得できた範囲の最後は UVC payload のログである。停止処理の完了、ファイルの整合性、端末がフリーズしたか、切断の原因はいずれも未確認。停止指示と切断の時間的な前後関係だけで、因果関係を断定しない。

端末の状態をユーザーに確認依頼中。復帰後は、まず既存ファイルと保存済みログを保全し、サービスの状態と必要なら再起動時の診断情報を読み取り専用で確認する。過去にフリーズを起こした usbfs の UAC claim/release は使っていない。ユーザーの状態確認前に追加の録画・再列挙・機器設定変更を行わない。

## 復帰後の読み取り検証

ユーザーから端末が再起動していたこと、その後さらに手動で再起動し、画面ロックを無効にしたことを確認した。再接続後のサービスは停止済みだった。最新の起動理由は `reboot,userrequested` で、直前のユーザー操作に対応するが、それより前の不調の原因は確定しない。最初の再接続時に取得した `/proc/last_kmsg` には `sys.powerctl='shutdown,shell'` があり、その時点の `sys.boot.reason` も同値だった。ただし last_kmsg の該当行は起動後50,835秒、試験時の音声ログの elapsedRealtime は約7,303秒であり、該当行を試験直後の記録と結びつけることはできない。この記録だけで操作主体や原因を特定しない。最初の取得と手動再起動後の別の取得をローカルに保存した。

試験ファイル `xreal_20261027_233636` は3種類とも残り、MP4 は約72.21秒・2048×1512 HEVC 4,289パケットと48 kHz AAC 1chを含む。WAV は70.5秒、左右合計771,770サンプルが非ゼロ。音声ログでは `systemSilenced=false`、USBマイクのルートが記録されていた。

- raw HEVC の全デコードで FFmpeg `-v error` の出力は0バイト。
- raw と MP4 抽出後の VCL NAL は4,289個すべて一致。
- MP4 の全 HEVC ヘッダを FFmpeg `trace_headers` で調べ、143 IDR 間の4,146 Pスライスの POC 連番に不連続0。これはこの録画での結果であり、19:36の異常が解決した証明ではない。
- 同時に取得した logcat の当該時間帯には4,292件の payload ログがあり、記録された EOF フラグはすべて true、連続する FID の同値は0だった。ログは UVC の全エラーや未記録 payload を網羅するものではない。

再現試験の端末不調と19:36の POC 異常の関係も未確定。追加の長時間録画は端末状態を確認し、停止・再起動に関する新しい証拠を評価した後に行う。

## 追加のユーザー情報と受信診断

ユーザーによると、最初の予期しない再起動まではスマートフォンに触れておらず、その再起動後に Samsung アプリが繰り返し停止していた。その後、ユーザーが手動で再起動した。端末不調の根本原因は本件の主目的ではなく、ログから録画アプリとの因果関係も確定できない。

UVC 受信側には、長い bulk 読み込み待ちと前回読み込み後の処理時間、読み込み失敗、短い payload、不正なヘッダ、UVC error フラグ、EOF 前の FID 変化の診断ログを追加した。計測値は経路の切り分け用で、長い待ち時間自体をエラー原因と断定しない。従来のフレームの組み立て・保存・HEVC パススルーは変更しない。この変更はローカルコンパイルで確認し、実機でのログは未検証。

さらに、連続する組み立て済み AU が512 bytes以上の完全な前方一致を示す場合、長さと AU 番号を logcat に記録する診断を追加した。データの破棄・書き換え・録画停止はしない。前方一致はあくまで調査の手掛かりであり、正常な映像でも起こりうる。比較関数は一致・不一致・短い入力・null をローカルでテストしたが、実機での検出と負荷は未検証。

組み立て前の新しい USB payload にも、前の AU と512 bytes以上の前方一致があるかを記録する診断を追加した。UVC ヘッダと HEVC 開始コードまでの不要データを除いた範囲を比較し、読み込まなかったバッファ末尾は比較しない。分割 payload でも警告が出る可能性があり、警告だけでは破損や発生源を確定できない。ローカルでオフセット・範囲外・一致・不一致をテストし、実機では未検証。

参考として、[AOSP Android 15 の UsbDeviceConnection JNI](https://android.googlesource.com/platform/frameworks/base/+/android-15.0.0_r1/core/jni/android_hardware_UsbDeviceConnection.cpp) では、bulk 要求時に Java 配列をネイティブの USB 転送へ渡している。これは公開ソース上の構造であり、SC-52B の Samsung ビルドの同一性や、今回のデータ異常の原因を示す証拠ではない。

保存済み `logs/goal_20261027_uvc_logcat.txt` 全体を再集計すると、`payload n=...` 行は13,180件で、記録された長さの最大は54,072 bytes、記録上のヘッダ長はすべて2、EOF はすべて true、既存フレーム長はすべて0だった。現行コードは EOF または65,536 bytes超の場合のみ payload 行を出すため、この集計は全 USB 読み込みの網羅的な検査ではない。また対象ログは19:36の異常録画時のログではない。従って異常時の入力や断片化、受信層の原因は判定できない。

## 診断付き長時間録画（2026-10-28 21:39）

診断付きアプリで録画し、通常操作で停止した。録画ファイルの長さは約576.76秒（9分37秒）で、予定した10分には達していなかった。停止後にサービス停止と ADB 応答を確認。HEVC 2048×1512、平均約59.39 fps、AAC 1ch。RAW HEVC の全復号では HEVC 参照エラーは出なかったが、null 出力側の DTS 非単調警告が1行出た。これだけで元 MP4 の時刻異常とは断定しない。RAW と MP4 抽出映像の VCL NAL は各34,252個すべて一致した。

受信ログでは21:40:07.993に `bulkTransfer` が一度 -1 を返し、前後の記録された payload の FID は交互で、その後も録画が続いた。前方一致・FID 途中変化・UVC error flag・不正ヘッダの警告は見つからなかった。失敗付近を含む MP4 の39〜44秒付近の HEVC ヘッダでは P スライス293個の POC 不連続は0（IDR 11個）。ただし IDR をまたぐ欠落はこの確認では検出できず、読み込み失敗の影響がないと証明するものではない。ログの末尾は収集停止で一部切れている。

音声ログには USB 入力 `systemSilenced=false` と、録画中の exact-zero 警告の開始・解除が記録されていた。これは入力途絶を確定するものではない。MP4 音声の `volumedetect` は平均 -60.4 dBFS、最大 -21.3 dBFSで全体としては非ゼロ。独立ステレオや内容同期は未確認。録画と診断ログは Git 管理外。参照エラーはこの試験でも再現せず、発生元は引き続き未特定。

同試験の WAV を後から実測した。48 kHz・32-bit・2ch、27,600,000フレーム（575秒）で、左右は全フレーム一致。左の非ゼロは7,514,967フレーム、ピークは189,005,824。WAV の266秒から277秒未満は、1秒単位の集計では左右とも全サンプルがゼロだった。ログの exact-zero 警告は録音開始を示す診断行から約275秒後に出ており、10秒連続ゼロを検出する設定と概ね整合する。ただし警告時刻と WAV のサンプル時刻の厳密な対応は未検証で、静かな環境・信号処理・入力途絶のどれかは特定できない。WAV は Git 管理外。

この長時間 MP4 の映像パケット34,252個を `ffprobe` で再検査した。時間基準は1/90,000秒で、PTS・DTS はいずれも全区間で単調増加し、同値や逆行は0。最小 PTS 間隔は30 tick（約0.333 ms）で、41.265秒付近に短い間隔が集中した。開始時刻とログ時刻を概算すると、この集中は前述の bulk 読み込み失敗後に複数 payload が連続した箇所と整合するが、厳密な時計の対応・発生源は未確認。RAW を null 出力した際の DTS 警告から、この MP4 に同値・逆行があったとは言えない。パケット時刻とログは Git 管理外。

長時間録画の RAW HEVC 全体について `trace_headers` を解析した。SPS の `log2_max_pic_order_cnt_lsb_minus4=4` に基づき、IDR 1,142個の後に P スライス33,110個の POC を256周期で調べたところ、IDR 間の不連続は0だった。IDR をまたぐ欠落は検出できず、全画像の完全性や過去の異常の解決を示さない。解析ログは `logs/uvc_long_all_headers.log`（Git 管理外）。

同じ長時間 MP4 の隣接する映像パケットを、先頭4 bytesの長さフィールドを除いて比較した。両パケットが516 bytes以上の組で、短い側の残り全体が長い側の先頭に一致した組は0（全34,252パケット）。19:36録画で見つかった、同一の先頭が段階的に伸びるパターンはこの条件では再現しなかった。正常性の一般的な保証や異常の発生層の特定ではない。

# 1600x1200 より横に画角が広い解像度の捜索結果 (2026-11-17)

## 結論

1600x1200 (4:3) より横方向に画角が広いのは、アスペクト比 16:9 の次のモード。

| モード | stream_type | fps | 1600x1200 比の横広角 |
|---|---|---|---|
| 1280x720 | 0x0b | 30 | 約 1.33x (16:9) ※実証済み |
| 1920x1080 | 0x04 / 0x05 | 30 / 60 | 約 1.33x (16:9) |
| 2560x1440 | 0x03 | 30 | 約 1.33x (16:9) |

最も実用的な候補は **1920x1080 / 60fps (stream_type=5)**。
横広角 (16:9) かつ 60fps かつファームウェア公式サポート。

**2026-11-17 実機検証による修正**: 2560x1440 (WQHD) はモード表に存在するが、
実機でカメラ Start (0x2781) が拒否され (応答 `22 02 08 01`)、ハードウェア非対応と判明。
Sensor は 12.19MP (4032x3024 photo) で WQHD 3.69MP は物理内だが、
pilot 内部の実行時ノード幅 2048 が実効上限で、幅 2560 はこれを超過する。
対して 1920x1080 (幅 1920 < 2048) は Start 応答 `22 00` で受理された。
したがって**実用可能な横広角は 1920x1080 のみ** (2560x1440 は除外)。
なお 1920x1080/60 もアプリ経由の録画は失敗しており、
3整数 (w,h,fps) のメモリ書換えだけでは内部 stream_type が追従しない。
実用化には stream_type=5 の設定経路の特定が必要。

## 2026-11-18 最終結論: 1920x1080 は設定不可能

解像度設定は TCP RPC `0x2780` (NRRgbCameraInitSetImageResolution) の
ペイロード `1a02 08 <code>` (protobuf field1 varint = stream_type) で行うことを特定。
グラスを再起動してクリーンな状態から `Create(0x277e) → SetResolution(0x2780, code)`
を送り、各 code の応答を網羅的にテストした:

| code | 応答 | 判定 |
|---|---|---|
| 4 (1920x1080/30) | `22 03 08 89 27` | 拒否 |
| 5 (1920x1080/60) | `22 03 08 89 27` | 拒否 |
| 9 (2016x1512/60) | `22 00` | 受理 |
| 10 (2016x1512/30) | `22 00` | 受理 |
| 11 (1280x720/30) | `22 03 08 89 27` | 拒否 |
| 12 (1600x1200/30) | `22 00` | 受理 |
| 13 (1600x1200/60) | `22 00` | 受理 |
| 15 (モード表外) | `22 00` | 受理 |

RGB カメラ (`librgb_camera.so`) が受理するのは 9,10,12,13,15 のみで、
**モード表に存在する 1920x1080 (code 4/5) と 1280x720 (code 11) は拒否される**。
したがって、このファームウェア (FW 1.9.1.20260820191100) では
1920x1080 はソフトウェア的に設定不可能であり、録画実装はできない。

3整数 (w,h,fps) のメモリ書換えで録画した場合も実出力は 1280x720/30 のままで
(VID_20261118_040803.mp4 で ffprobe 確認)、この経路では実ストリームは変わらない。

受理コード 15 はモード表に無く、旧解析では 2016x1512/60 候補とされているが、
実映像の確認は未実施 (Start が `22 02 08 05` で拒否され、Create 再実行等が必要)。

結論: **1600x1200 より横に広い画角の解像度を実機で録画することは、
このファームウェアでは不可**。実用可能な最大モードは 1600x1200/60 (code 13) または
2016x1512 (code 9/10、4:3 なので横画角は 1600x1200 と同等)。


## 根拠 1: ファーム웨어の pilot モード表

`libcamera_service.so` (SHA-256 先頭 `0513947206120f31`, HANDOFF 記載の実機一致ハッシュ)
の文字列テーブルを静的解析。起点 `0x3df18`、ストライド `0x18` (24 bytes)、14 エントリ。

```
stream_type= 0 (0x00): pilot 504x378 60fps
stream_type= 1 (0x01): pilot 504x378 30fps
stream_type= 2 (0x02): pilot 504x378 15fps
stream_type= 3 (0x03): pilot 2560x1440 30fps
stream_type= 4 (0x04): pilot 1920x1080 30fps
stream_type= 5 (0x05): pilot 1920x1080 60fps
stream_type= 6 (0x06): pilot 1440x2560 30fps
stream_type= 7 (0x07): pilot 1080x1920 30fps
stream_type= 8 (0x08): pilot 1080x1920 60fps
stream_type= 9 (0x09): pilot 2016x1512 60fps
stream_type=10 (0x0a): pilot 2016x1512 30fps
stream_type=11 (0x0b): pilot 1280x720 30fps
stream_type=12 (0x0c): pilot 1600x1200 30fps
stream_type=13 (0x0d): pilot 1600x1200 60fps
```

補足: 旧 HANDOFF の「コード3 = 720p/60」「コード5 = 1080p/60」は不正確。
正しくはコード3 = 2560x1440/30、コード5 = 1920x1080/60。
720p は 30fps (コード11) のみが公式。720p/60 は文字列テーブルに存在せず、
このファームウェアで設定から再有効化できない (11/17 実機検証済み) ことと整合する。

## 根拠 2: 保存済み実データの解像度分布

全 .cache/*.mp4 を ffprobe した結果:

| 解像度 | 本数 | アスペクト比 |
|---|---|---|
| 1280x720 | 59 | 16:9 (1.78) |
| 1600x1200 | 28 | 4:3 (1.33) |
| 2016x1512 | 3 | 4:3 (1.33) |
| 2048x1512 | 1 | 4:3 (1.35) |

1920x1080 / 2560x1440 の実録画は存在しない (未検証)。
2016x1512 の 3 本は復号ノイズ (過去の不正設定試験) で画角比較不能。

## 根拠 3: アスペクト比と実測画角

同じ垂直センサー領域を使うと仮定し、高さ 1200px に正規化した横幅:

- 4:3 (1600x1200, 2016x1512, 504x378, 4032x3024): 横 1600px
- 16:9 (1280x720, 1920x1080, 2560x1440): 横 2133px (約 33% 広い)

11/14 の SIFT 実測 (HANDOFF) で 1600/30 vs 720/30 は 720 側が左右に広く、
1600 側画像の局所スケール中央値 0.754 (= 720 が約 1.33x 広い) であり、
16:9 が横広角であることは実データで確認済み。

## 未検証 / 今後の課題

- 1920x1080 / 2560x1440 を実機で設定し、録画・画角を検証する。
  設定は stream_type を 5 / 3 にするか、pilot メモリの 3 整数を
  (1920,1080,60) / (2560,1440,30) に書く方法が候補。
  ただし 720p/60 の事例 (11/17) では 3 整数書換えだけではカメラが Start を拒否したため、
  内部の解像度選択コード (stream_type) も同時に設定する必要がある可能性が高い。
- 今回はスマホ (haven-sc-52b) が Tailscale オフラインで実機検証なし。
- 実機・端末設定の変更は行っていない。
